# Локальный сайт производственных отчётов

Сайт на рабочем компьютере, который принимает свободную переписку мастеров по
намоточным станкам — текстом, файлом или фотографией, — накапливает её за
смену и по одной кнопке собирает отчёт производства за день по каждому станку,
с выгрузкой в Excel по рабочему бланку и файлом для 1С.

Раньше это был Telegram-бот. Все функции переехали на сайт без изменений:
тот же накопитель смены, тот же разбор ИИ, тот же расчёт часов кодом, те же
ответы — поменялся только интерфейс.

## Как этим пользоваться

`python main.py` — сервер поднимется на `http://127.0.0.1:8080` и сам откроет
страницу. Остановить — Ctrl+C. Тем, кому консоль не нужна, подходит сборка в
один файл `production-reports.exe` — двойной клик, без окна консоли (см.
раздел «Запуск без консоли»).

Пять разделов на странице: **Данные смены**, **Отчёт за дату**, **Готовые
файлы**, **Сводный отчёт**, **Журнал**.

1. **Пишете, кто прислал** (поле «кто прислал» — оно подписывает каждую
   загрузку в журнале) и **кидаете данные как удобно**: текстом в поле,
   файлом переписки или фотографией — кнопкой или перетаскиванием. Сайт
   отвечает «✅ Данные приняты», пишет, что увидел (станки, счётчики, метки
   времени), и складывает сообщение в накопитель смены. **ИИ на приёме не
   вызывается** — приём бесплатный. Фото тут же проходят бесплатное
   распознавание: без текста не сохраняются, с текстом не по делу —
   откладываются отдельно (см. раздел про OCR).
2. **Открываете «Отчёт за дату»**, выбираете дату и нажимаете «Собрать
   отчёт» — сайт делает **один** запрос к ИИ сразу по всей накопленной за
   смену переписке и всем фото, считает часы кодом и отдаёт отчёт по каждому
   станку + файл Excel. Сборка идёт в фоне: страница показывает её статус,
   запрос к серверу не висит, и второй клик по той же дате не запускает
   второй запрос.
3. Данные после отчёта не стираются: можно доприслать сообщения и собрать
   отчёт заново — новые файлы заменят старые. «Очистить смену» — стереть
   накопленное (готовые файлы при этом остаются).

Смена по умолчанию **07:00–19:00**. Дату смены сайт берёт из переписки
(«20 августа 2026 г.», «20.08.2026»), а если её нет — считает, что данные за
текущую смену.

### Почему так, а не разбор каждого сообщения через ИИ

Дешевле и точнее. За смену приходит 20–40 сообщений; если гнать каждое через
модель, это 20–40 запросов вместо одного, и токены расходуются на один и тот
же контекст. А главное — по одному сообщению отчёт не собрать: начальное
показание счётчика приходит утром, конечное вечером, подмены — в середине
дня. Поэтому приём работает на встроенных регулярках (только чтобы ответить
«принято» и показать, что распознано), а ИИ вызывается один раз на всю смену.

## Возможности

- 📥 Накопитель смены: любое сообщение (текст/фото/текст+фото) сохраняется
  как есть, без команд и без обращения к ИИ
- 📄 Приём **файлом** (.txt/.docx/.xlsx/.json/.html/.pdf): выгрузка чата
  целиком, разделы «–151», «–251» читаются как заголовки обсуждений, поэтому
  станок каждого блока известен точно (см. «Приём переписки файлом»)
- 📊 Отчёт за день по каждому станку: выпуск и время работы по счётчику и
  норме, подмены, срезы, простои с причинами словами мастеров
- ⏱ Баланс времени станка (12 ч) и сотрудника с пометкой недостатка времени
- 📄 Выгрузка в Excel по рабочему бланку «Отчет производства за смену» и
  файл для 1С
- 🗄 Архив готовых файлов: скачиваются заново без нового запроса к ИИ
- 📒 Журнал: кто прислал данные, что разложилось по станкам, чем кончилась
  каждая сборка отчёта
- 🖼 Бесплатный OCR фотографий: фото без текста не хранятся, рабочий текст
  уходит в отчёт, посторонний — отдельным списком
- ⚠️ Подсветка пропусков: нет счётчика, не указан номер станка, нет нормы

## Технологии

- Python 3.9+
- HTTP-сервер на stdlib (`ThreadingHTTPServer`) + одна страница на чистом
  HTML/CSS/JS — без сборщика и без внешних сайтов
- JSON-API (`webapp/api.py`), функциональный слой `services/` про HTTP ничего
  не знает
- Фоновые задачи (`webapp/jobs.py`): сборка отчёта живёт в своём потоке,
  страница опрашивает статус
- SQLAlchemy 2.0 — работа с базой данных
- SQLite — база данных
- Регулярные выражения — базовый разбор свободного текста
- Опционально ИИ (Claude / OpenAI-совместимый шлюз) — разбор грязной переписки и фото; клиент на stdlib `urllib`, без доп. зависимостей
- Чтение файлов на чистом stdlib (`zipfile` + `xml.etree`) для .docx/.odt/.xlsx; опционально `pypdf` — только для PDF

## Приём переписки из Яндекс Мессенджера (заготовка)

Сейчас данные присылают на сайт. Следующий этап — забирать их прямо
из рабочего чата, где порядок такой:

```
руководитель:  91 машина информация за смену 20.08.2026     ← корень обсуждения
рабочие:       данные по этой машине — ответами в обсуждении
```

Это лучше, чем разбор сплошного текста: **номер станка и дату даёт заголовок
обсуждения**, а не догадка по тексту («251» у мастера может быть и станком, и
количеством шпуль). Поэтому модуль `services/yandex_source.py` группирует
сообщения по обсуждению, а карту «обсуждение → станок, дата» помнит между
опросами (заголовок написан утром, ответы идут весь день).

Заготовка уже работает без доступа к API — на сохранённом JSON:

```bash
python -m services.yandex_source --file tests/yandex_updates_sample.json
python -m services.yandex_source --file dump.json --dry-run   # только показать
python -m services.yandex_source --poll                       # после доступа
```

Принятые сообщения ложатся в тот же накопитель `data/shifts/<дата>/day.json`,
поэтому отчёт и Excel формируются ровно как сейчас — для расчёта нет разницы,
пришло сообщение через сайт или из Мессенджера.

Когда доступ дадут, подставить нужно **ровно две функции**: `_api_get()` (один
HTTP-запрос за сообщениями) и `_download_file()` (скачать вложенное фото).
Разбор ответа заранее написан терпимо к именам полей (`text` / `body` /
`message_text`, автор строкой или объектом, `thread_id` /
`reply_to_message_id`), так что реальный ответ, скорее всего, подойдёт без
переписывания. Настройки — `YANDEX_*` в `.env` (`.env.example` заполнен
подсказками), токен только там.

Что модуль делает сам: пропускает заголовки (в них нет данных), не задваивает
сообщения при повторном опросе, сохраняет сообщение даже если фото не
скачалось, и предупреждает, если станок из заголовка отсутствует в
`services/machine_rates.json` или если в ветке не нашёлся заголовок.

## Фотографии из чата: бесплатный OCR до вызова ИИ

В рабочем чате фото кидают постоянно, и чаще всего это «показать, что
сделано»: намотанный материал, катушка, рабочее место. Данных смены там нет,
а токены за картинку списываются. Поэтому каждое фото на приёме проходит
**бесплатное** распознавание локально (Tesseract, без сети и без оплаты), и
по результату решается одно из трёх:

| Что на фото | Что делает сайт |
|---|---|
| текста нет | фото не сохраняет и в ИИ не отправляет |
| текст рабочий (счётчик, время, «шпули», «подмена»…) | в ИИ уходит **распознанный текст**, а не картинка |
| текст есть, но не про работу | в отчёт не включает, показывает отдельным списком «📎 Постороннее с фотографий» |

«Рабочий» текст определяется по признакам смены: показание счётчика (5–8
цифр), время `07:00`, дробь «1362 из 2030», слова смены. Цифры — главный
сигнал, и они не зависят от языка, поэтому фильтр работает даже без русского
языкового пакета.

Посторонний текст не пропадает молча: он выводится списком с номером
сообщения и именем файла, а сама фотография остаётся на диске. Если OCR
ошибся и там всё-таки данные, это видно сразу.

**Цена решения, о которой честно:** Tesseract читает рукописный журнал хуже,
чем зрение модели, и может перепутать цифру. Поэтому распознанный текст
помечается в запросе как «автоматически с фото, возможны ошибки», а если
качество не устроит — в `.env` есть `OCR_SEND_PHOTOS_TO_AI=true`, и картинки
снова пойдут в модель без правки кода.

Если Tesseract не установлен, фото **не теряются**: они уходят в ИИ картинкой,
как раньше, а сайт один раз честно предупреждает. Установка на Windows:

```bash
py -m pip install -r requirements.txt
# плюс сама программа: установщик «Tesseract at UB Mannheim»,
# при установке отметить Russian (Additional language data)
```

Если программа не в PATH, укажите путь в `.env`:

```env
TESSERACT_CMD=C:\Program Files\Tesseract-OCR\tesseract.exe
```

Проверка на настоящих картинках (рисуются в тесте):

```bash
python tests/test_photo_ocr.py
python -m services.photo_ocr путь\к\фото.jpg   # посмотреть, что видит OCR
```

## Установка

### 1. Клонирование репозитория

```bash
git clone https://github.com/zamaletdinovr575-web/ForWorkTest.git
cd ForWorkTest
```

### 2. Установка зависимостей

```bash
pip install -r requirements.txt
```

### 3. Настройка переменных окружения

Скопируйте файл `.env.example` в `.env`:

```bash
cp .env.example .env
```

Заполните переменные в файле `.env`:

```env
# Сайт: адрес и порт. 127.0.0.1 — доступ только с этого компьютера.
WEB_HOST=127.0.0.1
WEB_PORT=8080

# База данных (журнал загрузок и сборок)
DATABASE_URL=sqlite:///./web_database.db

# Логирование
LOG_LEVEL=INFO
LOG_FILE=logs/web.log

# ИИ для разбора переписки (без него отчёт упрощённый, без Excel)
AI_ENABLED=true
AI_API_KEY=ваш_ключ
AI_BASE_URL=https://api.anthropic.com
AI_MODEL=claude-opus-4-20250514
AI_API_FORMAT=anthropic
```

Токенов для запуска не нужно: сайт локальный и работает без внешних сервисов.
Ключ ИИ — единственное, что здесь секрет: в `.gitignore` он не проходит,
`.env` в репозиторий не коммитится.

Если `WEB_HOST` поставить не `127.0.0.1` (например, `0.0.0.0`, чтобы зайти с
другого компьютера цеха), сайт откроется наружу — пароля на нём нет, доступ к
переписке и счётчикам получит любой в сети.

Два промаха, на которых ловятся оба раза, когда модель «не меняется»:

* `AI_MODEL` — **точный идентификатор** модели у шлюза, а не красивое имя с
  его сайта. Шлюз показывает «Claude Fable 5.1», а принимает `claude-fable-5.1`;
  с пробелом и заглавными отвечает `HTTP 404 model_not_found`. Точные id —
  в ответе `AI_BASE_URL/models`.
* `.env` читается **один раз при запуске**. Пока процесс жив, правка модели до
  отчёта не дойдёт, а второй двойной клик по `.exe` — не перезапуск, а «открой
  страницу ещё раз»: её продолжит обслуживать прежний процесс. Поэтому в шапке
  лога и в бейдже «ИИ: …» на странице печатается модель, на которой сидит
  текущий запуск, — по ней сразу видно, что ты смотришь на старый процесс.
  Перезапуск: снять задачу в диспетчере и кликнуть снова.

## Запуск без консоли: один .exe

Чтобы не объяснять человеку в цеху про Python и консоль, сайт собирается в
один файл: двойной клик по нему поднимает сервер и открывает страницу, окна
консоли при этом нет.

Сборка (один раз, на компьютере, где уже стоят зависимости):

```bash
py -3.11 -m pip install pyinstaller
py -3.11 -m PyInstaller --noconfirm --distpath . production-reports.spec
```

Получится `production-reports.exe` в корне проекта — `--distpath .` кладёт его
рядом с `.env`, `data/` и `logs/`. Имя можно поменять на любое: программа ищет
свои файлы по папке, в которой лежит сама.

Как это работает и что нужно знать:

* **`.exe` должен лежать в одной папке с `.env`** — оттуда берутся адрес, порт
  и ключ ИИ. Именно поэтому сборка кладёт файл в корень проекта; переносить на
  другой компьютер его можно только вместе с `.env` (внутрь `.exe` секрет не
  укладывается, и в этом плюс: файл можно отдать кому-то без ключа);
* переписка смены, готовые отчёты, база и логи пишутся **рядом с `.exe`**
  (`runtime_paths.py`), а не во временную папку, из которой `.exe` распакуется и
  исчезнет вместе с данными;
* остановить — снять задачу `production-reports.exe` в диспетчере задач;
  повторный двойной клик не ошибка: занятый порт ловится, лишняя копия процесса
  сообщает «сайт уже запущен» и выходит, а страница остаётся открытой;
* ошибки запуска показываются окном с текстом, а подробности пишутся в
  `logs/web.log` — консоли-то нет;
* Tesseract в `.exe` не входит: это отдельная программа, и без неё фотографии
  уходят в ИИ картинкой, как и раньше.

## Суточный отчёт (агрегация переписки за смену)

Когда за день по одному станку приходит много сообщений от разных мастеров,
сайт собирает из них **один** отчёт: счётчики, дроби (срез/подмена/навито),
список операторов и полную хронологию событий с временем (обед, простой,
пуск, подмена, переналадка, конец смены и т.д.). Смена по умолчанию —
**07:00–19:00**.

Накопленное лежит в файлах рядом с сайтом и правится руками:

```
data/shifts/20.08.2026/day.json      # сообщения смены по порядку + отпечатки
                                     # принятых файлов (повтор не дублирует)
data/shifts/20.08.2026/photos/*.jpg  # приложенные фотографии
```

В разделе «Отчёт за дату» список дат берётся по накопленным сменам, а по
умолчанию отмечена та, в которую добавляли данные последней. Готовые файлы за
любую дату — раздел «Готовые файлы», там же видно, что накоплено, но ещё не
собрано.

Проверить агрегацию на текстовом файле, без запуска сайта и без внешних API:

```bash
python tests/test_daily_report.py                 # на встроенном примере
python tests/test_daily_report.py path/to/day.txt # на своём файле
```

> Автоматическая выгрузка переписки из Яндекс Мессенджера/360 — отдельный
> будущий этап (нужен Yandex API). Логика агрегации от источника не зависит:
> тот же текст можно будет подавать из API в `build_daily_reports()`.

## Сменный отчёт по станку (время работы по счётчику)

Сайт формирует подробный отчёт по каждому станку за смену — как в ручном
«Отчёте производства за смену». Время фактической работы станка считается
**из показаний счётчика и нормы выработки**, а не из интервалов сообщений:

```
Выпуск, узл.    = счётчик_конечное − счётчик_начальное
Время работы, ч = Выпуск / (узлов в минуту) / 60
```

«Узлов в минуту» — норма на конкретный станок, хранится в
`services/machine_rates.json` (столбец «кол-во отходов в минуту» из отчёта).
В справочнике все девять станков участка: 98, 111, 121, 151, 251, 321, 601,
14тр, 15тр. Файл редактируемый: правьте нормы без изменения кода. Если в
переписке встретится номер, которого в справочнике нет, это скорее опечатка
мастера — сайт не считает время «на глаз», а пишет «нет нормы выработки».

Что попадает в отчёт: выпуск и время работы по каждому ассортименту/заявке,
подмены (кол-во, часы, кто подменял), срезы, технические остановки с
причинами и итоги смены.

### Почему станок простаивал

Причина простоя берётся из сообщений мастеров: «машина стоп, произвожу
подмену», «стоит, навиваю шпули», «остановка — нет оператора». ИИ достаёт
время и формулировку, а код относит её к категории (навивка/намотка шпулей,
подмена, наладка/переналадка, ремонт, отсутствие оператора, ожидание сырья,
внешние причины) и решает, **работал ли в это время оператор**. Это ключевое
различие: навивка и наладка — работа сотрудника при остановленном станке, а
отсутствие или ожидание сырья — нет.

### Баланс времени и недостаток

```
Станок:     работа по счётчику + простой с причиной = 12 ч
Сотрудник:  время при работающем станке + свои операции при остановке − обед
            = его смена − обед − часы на другом станке
```

Норма станка — **12 ч** (07:00–19:00). Норма сотрудника считается от **его
смены**: если смена до 15:30, это 8,5 ч, минус обед (45 мин, или 30 мин при
смене до 15:30), минус часы, отработанные на другом станке. Пример: навивка
шпулей 3 ч + работа станка 8 ч = 11 ч работы сотрудника — норма.

Расхождение **до 20 минут** считается нормой и не помечается. Если больше —
в отчёте появляется «⚠️ НЕДОСТАТОК ВРЕМЕНИ» отдельно по станку и по
сотруднику. Если сумма превысила 12 ч — значит, часы простоя задвоены или
пересекаются, это тоже помечается.

**Оператора перевели на другой станок.** Фразы «оператор переведён на 251»,
«навивка шпулей на 251» разбираются как часы, засчитанные *тому* станку:
для этого станка это простой с причиной, но из нормы его сотрудника эти часы
вычитаются — иначе одни и те же часы посчитались бы дважды на двух станках.
Операция на своём станке («переведена на навивку шпулей») остаётся в его
времени.

**Когда данных не хватает — отчёт не выдумывает недостаток.** Если у станка нет
нормы в `machine_rates.json` или в переписке нет пары показаний счётчика,
время работы неизвестно, и вместо ложного «НЕДОСТАТОК 12 ч» отчёт пишет
«⛔ Баланс времени не считаю: …», а в Excel в клетке недостатка стоит
«нет данных». Неполные показания счётчика отдельно перечисляются в блоке
«⚠️ Проверьте данные».

**Простои без времени.** Мастер часто пишет причину без часов: «крючок не
взял петлю», «вызываю наладчика», «чинка пропуска». Такие строки не
выбрасываются: они идут в отчёт разделом «🕓 Простои без времени», а в Excel —
строкой «простой без времени» с пустой клеткой часов (заполните руками). Если
у станка есть недостаток времени, отчёт прямо пишет, что это скорее всего
они — а не «неизвестно куда ушли 4 часа».

### Выгрузка в Excel

Вместе с текстовым отчётом сайт отдаёт файл `.xlsx` из трёх листов:

- **«Отчет за смену»** — ваш бланк один в один (колонки A–T, те же
  заголовки). Выпуск и время — формулами `N=M−L` и `O=N/T/60`, поэтому файл
  пересчитывается, если поправить счётчик или норму руками. Синим — ячейки
  для ручного ввода.
- **«Простои по причинам»** — расшифровка простоя с формулировкой мастера и
  признаком «оператор работал» (он решает, идут ли часы в время сотрудника).
- **«Итоги смены»** — баланс станка и сотрудника с пометкой недостатка,
  тоже формулами (`SUMIFS`), плюс описание методики на самом листе. Есть
  строка «Отработано на другом станке», которая вычитается из нормы.

На сайте: раздел «Отчёт за дату» — по всему, что накоплено за смену. Отдельных
команд для «часов» и «суток» нет: данные присылаются обычными сообщениями,
отчёт собирается кнопкой.

Проверка расчёта без сети (сверка с эталонными числами Excel):

```bash
python tests/test_shift_report.py     # формула, причины простоя, допуск 20 мин
python tests/test_excel_export.py     # структура бланка и формулы выгрузки
python tests/test_day_19_08_2026.py   # реальный день, 6 станков: текст = Excel
python tests/test_day_20_08_2026.py   # реальный день, 6 станков: простои без времени
python tests/test_shift_store.py      # накопитель смены: дата, разбор, сброс
python tests/test_site_flow.py        # весь сценарий: приняли → отчёт + Excel
python tests/test_webapp.py           # JSON-API сайта, фоновые сборки, журнал
python tests/test_yandex_source.py    # приём из Мессенджера по обсуждениям

```

Последние тесты — регрессия на настоящей переписке за 19.08.2026 и 20.08.2026
(станки 98, 321, 251, 151, 121, 111) и полный прогон сценария сайта (с
подменённым ИИ, без сети). Первый сверяет расчёт с сообщением
мастера: по счётчику станка 111 получается 28 минут работы — ровно столько,
сколько он написал. Второй ловит случаи из жизни: станок, который всю смену
стоял на подмене и переналадке (баланс всё равно 12 ч), станок без конечного
показания счётчика («нет данных», а не недостаток) и оператора, который весь
день работал на чужих станках.

> Время работы берётся из счётчика и нормы, поэтому в переписке обязательно
> должны быть начальное и конечное показания общего счётчика, а станок —
> присутствовать в `machine_rates.json`.

## Разбор через ИИ и фотографии сообщений

Реальная переписка в чате мастеров грязная: заголовки сообщений
(«Имя, 07:03:»), цитаты-ответы, ссылки на станок вида «√251», несколько
станков в одном потоке, а часть данных приходит **фотографиями**. На таком
регулярки ошибаются. Поэтому подключается нейросеть (Claude или
OpenAI-совместимый шлюз).

Схема гибридная и надёжная: **ИИ достаёт структуру** (делит по станкам,
выкидывает мусор чата, читает фото), а **детерминированный код** считает
часы и суммы — арифметика не зависит от «фантазии» модели.

Включение — через `.env` (ключ заполняете сами, в репозиторий он не
коммитится):

```env
AI_ENABLED=true
AI_API_KEY=ваш_ключ
AI_BASE_URL=https://api.anthropic.com   # или адрес вашего шлюза
AI_MODEL=claude-opus-4-20250514         # название модели у вашего шлюза
AI_API_FORMAT=anthropic                 # или openai
```

Если `AI_ENABLED=false` или ИИ недоступен, отчёт за день не пропадает: сайт
предупреждает и отдаёт упрощённую сводку по накопленному тексту (регулярками,
без расчёта часов по счётчику и без Excel). Приём сообщений от ИИ не зависит
вообще — он работает всегда.

`AI_MAX_TOKENS` по умолчанию 8192: за смену по 5–6 станкам структура ответа
получается большой, в 4096 она уже не влезает.

Проверить гибридный расчёт без обращения к сети (на заранее заданной
структуре, которую должен вернуть ИИ):

```bash
python tests/test_ai_pipeline.py
```

## Использование

### Разделы страницы

- **Данные смены** — поле «кто прислал», текст, файл и фото (кнопкой или
  перетаскиванием). Ответ сайта тот же, что раньше приходил в чат: что
  увидел, сколько накоплено.
- **Отчёт за дату** — список накопленных смен и сборка отчёта по выбранной.
  Сборка идёт в фоне, статус виден на странице; второй клик по той же дате
  не запускает второй запрос к ИИ. «Пересобрать без ИИ» проигрывает сохранённый
  разбор бесплатно. Если отчётов ИИ не дал вовсе, в чат уходит резервная
  сводка регулярками (`daily_report` по шапкам «Конец(начало) смены»): она
  раскладывается по станкам темы и берёт ПОСЛЕДНЕЕ показание счётчика в
  блоке — итог смены главнее приёмки (24.09.2026 первым прогоном было одно
  «станок не определён» с 3083 в роли общего счётчика). Строка вида «-12 шт.
  годные в работу» — это количество шпулей, а не станок №12: по такому заголовку
  тема не режется, иначе у настоящей 251-й оставался бы утренний счётчик
  (15.09.2026). Если смена легла в базу кусками и в продолжении нет заголовка
  станка, сводка помечает это словами «часть переписки не размечена по станкам»
  — показание может быть не вечерним, сверяйте с листом «Остатки».
- **Готовые файлы** — что собрано за дату, скачивание без нового запроса к ИИ
  и «что накоплено, но ещё не собрано».
- **Сводный отчёт** — один Excel по всем сменам, лист на дату. Там же
  «Очистить смену» (готовые файлы остаются).
- **Журнал** — последние загрузки и сборки: кто прислал, что разложилось по
  станкам, чем закончилась каждая сборка.
- **Помощь** — эта справка прямо на странице.

### Как присылать данные

Наберите текст в поле «Данные» (или перетащите файл/фото) и укажите, кто
прислал. Команд не нужно, сайт ответит «Данные приняты». Пример:

```
– 251
08:46 начало работы Об.сч.: 865637
Ср. сч.: 1362 из 2030
Завиты все шпули 502 шт.
Привязано 1261 узл.
Конец смены 20:00
```

Присыдать можно сколько угодно сообщений за смену и по нескольким станкам —
всё накопится. Когда данные закончились, откройте «Отчёт за дату» и соберите
отчёт.

> Обязательно указывайте **номер станка** хотя бы в одном сообщении и
> **начальное и конечное показания** общего счётчика — без них время работы
> станка не считается, и сайт честно напишет «нет данных» вместо цифры.

## Приём переписки файлом (рекомендуемый способ)

Проблема сообщений — в источнике. Мессенджеры режут длинный текст на части
(Telegram — по 4096 знаков), и разрез попадает **посередине обсуждения
станка**. Реальный прогон 10.09.2026: заголовок «–251» уехал в первое
сообщение, а «Конец смены … Общий сч.: 278755» — во второе. Хвост остался без
станка, и показания 251-й уехали на №151. Кроме того, выгрузка чата теряет
переводы строк, и текст слипается в кашу: «ср сч 57688:18 обрыв устранен …
машина в работе8:23 стоп машина» — это «ср сч 5768», время «8:18» и следующий
стоп в «8:23».

Файл приходит **целиком**, поэтому обеих проблем просто нет. На сайте длинный
текст можно вставить и в поле — он не порежется, — но файл надёжнее: в нём
сохраняются разделы и авторы.

### Как прислать

Перетащите файл в карточку «Данные смены» (или выберите его кнопкой) — без
команд, подпись необязательна:

```
📎 10,09,2026.docx      ← выгрузка чата из Word/Блокнота/Excel
   «вот смена за 10.09» ← подпись тоже сохранится
```

Сайт ответит:

```
📄 Файл «10,09,2026.docx» прочитан (документ Word) · смена 10.09.2026
Разложил по станкам: №151, №251, №321, №98 (4 разделов)
Станок каждого раздела взят из заголовка обсуждения, поэтому показания
не перепутаются между машинами.
Вижу авторов: Инна Гудкова, Юлия Черныш, Татьяна Арташина, Олег, Белякова С.
```

### Поддерживаемые форматы

| Формат | Чем читается | Примечание |
| --- | --- | --- |
| `.txt` `.log` `.md` `.csv` `.tsv` | stdlib | кодировки UTF-8/UTF-16/cp1251/cp866 определяются сами |
| `.docx` | stdlib (`zipfile`+XML) | **лучший вариант**: выгрузка чата из Word |
| `.odt` | stdlib | LibreOffice Writer |
| `.xlsx` `.xlsm` | `openpyxl` | по строке на строку листа, ячейки через « \| » |
| `.json` | stdlib | выгрузка 1С и дампы чата |
| `.html` `.htm` | stdlib | разметка убирается, переносы блоков сохраняются |
| `.pdf` | `pypdf` (опционально) | скан-картинку не читает — её присылайте фото |
| `.doc` `.xls` `.rtf` | — | сайт объяснит, как пересохранить |

Ограничения: файл до 8 МБ, текст до 400 000 символов. Ошибки (формат не тот,
файл пустой, слишком большой) возвращаются **понятным текстом**, а не
трассировкой — данные при этом не сохраняются, ничего не теряется.

### Что даёт файл

1. **Станок известен точно.** Разделы «–151», «–251», «–98» читаются как
   заголовки обсуждений и пишутся в накопитель полем `machine` — так же, как
   заголовок темы в Яндекс Мессенджере. Модель его не угадывает: «251» в
   тексте мастера могло быть и количеством шпуль.
2. **Остатки сырья не путаются.** Каждый замер «Конец(начало) смены» ложится
   на свой станок: счётчик 98-й больше не уезжает на 151-ю.
3. **Строки не слипаются.** Абзацы документа сохраняются, поэтому
   `split_glued_text()` почти не нужна (она остаётся как страховка для
   сообщений и OCR).
4. **Ничего не режется.** Одна секция = одно сообщение в накопителе.
5. **Повтор файла не множит данные.** Файл с тем же текстом, присланный в эту
   же смену второй раз, сайт принимает без добавления сообщений: иначе каждое
   обсуждение станка ушло бы в ИИ дважды, и модель удвоила бы количества.
   Отпечаток считается по извлечённому тексту, поэтому пересохранённый файл
   («те же буквы, другие байты») тоже узнаётся. Исправленный файл — другие
   данные → принимается; сброс смены («Очистить смену») снимает запрет.

Файл и обычные сообщения за одну смену **не конфликтуют**: можно прислать
выгрузку утром, а вечером дослать уточнение текстом или фотографией.

### Выгрузка темами: `дата_время;тип;автор;текст`

Так выгружают чат мессенджеры (проверено на `22.09.2026.csv` из Telegram):
никаких шапок «–151», вместо них **тема** — первое сообщение блока
«151 машина(Арташина) - информация за смену 22.09.2026г.», а все «Ответ» под
ней относятся этому станку. Разбирается тем же кодом, что и живые обсуждения
Яндекс Мессенджера (`services/yandex_source.parse_thread_header`), поэтому
станок темы известен точно и для файла, и для Мессенджера.

Терпимо к тому, что выгрузка гуляет от файла к файлу: разделитель `;`,
табуляция или запятая; дата `2026-09-22` или `22.09.2026`; без колонки «Тип»;
без строки заголовка; кавычки с точкой с запятой внутри текста; эхо заголовка
первым ответом; `14т` и `14тр` — один станок. Непонятный файл (нет тем,
посторонняя таблица) раскладывается **прежним** способом — одним блоком, и
сайт скажет об этом в ответе; ничего не выбрасывается молча.

### Чего в листе «Остатки» быть не должно

Килограммы в переписке бывают разные, и в сдачу за смену идёт не всякое число.
Не записываются и не требуют от мастера «назовите вид отходов»:

* **вес единицы сырья** — «бобины по 0,925кг», «1 шт 2,6кг», «катушек (весом
  ± 1,400 кг)», и просто размер бобины в скобках: «на их место маленькие
  (1,400 кг)» (ст.321 за 26.09.2026);
* **границы диапазона** — «от 3,8кг до 4,2 кг», «1,405кг-1,410кг»;
* **вес, названный примерно** — «ориентировочным весом 1,11кг»: его не
  взвешивали, подписывать вид отходов под него некому;
* **брак, переданный в лабораторию** — «общий вес 6,1 кг, бобины будут переданы
  в лабораторию» (ст.251 за 25.09.2026): нитка уехала поставщику на проверку, а
  не в отходы смены;
* **число из примера записи** — «произвести запись например ( шпиндель 3,
  шпули с 20 по 25 , вес 0.12 кг)» (ст.251 за 26.09.2026): руководитель
  показывает формулировку журнала. Пример опознаётся только пока между
  «например» и числом нет закрывающей скобки, поэтому настоящая сдача,
  написанная после примера, учитывается по-прежнему.

Хозяин сдачи — **шапка раздела выгрузки** («–251 машина»), как и у показаний
счётчика: «Вес нити после развивки шпулей =13 кг», написанный внутри раздела
251-й, принадлежит 251-й, даже если сводку прислала тема другой машины
(14.09.2026). Вид отходов мастер иногда пишет именительным падежом с большой
буквы — «Развивка 3х шпуль окончена Вес 2,8кг» (ст.251 за 26.09.2026); такая
форма тоже считается видом. Строчная «развивка» в описании работы («10:59
развивка шпуль в кол-ве 750шт окончена») — нет: иначе одна и та же сдача
ложилась бы двумя видами, а бланк в конце смены её уже подписал.

Выгрузка чата вставляет пробел после десятичной запятой — «Вес отходов после
подмены 10, 4кг». Это 10,4 кг, а не «4 кг»: иначе станок получал бы вторую
несуществующую сдачу.

Станок, которого нет в переписке смены (модель родила его из размера полотна
«187х6-100,0-151,5»), выбрасывается из отчёта **и из журнала счётчиков**
(`counter_ledger.json`): оставленная там запись за эту дату завтра стала бы
«началом смены» настоящего станка. Если сам журнал записать не удалось (нет
места на диске, каталог закрыт другим процессом), сайт говорит об этом в
ответе — молча потерянный журнал значит, что следующая смена начнётся с
неизвестно какого числа.

### Разметка мессенджера внутри бланка

Мастер выделяет жирным весь бланк, и из выгрузки приезжает
«**Общ.сч**. -226571______». Маркер со звёздочками внутри не узнавался, и
показания станции терялись: прогон 25.09.2026, ст.111 — в «Остатках» ни одного
счётчика; 24.09 ст.111 и 21.09 ст.151 — вместо конца смены напечатано утреннее
число. `remains_report.normalize_text` снимает серии звёздочек перед поиском
маркеров. Подчёркивания НЕ трогаем: ими мастера заполняют пустые клетки бланка
(«_3001____ из 2700____»), и «__» как признак полужирного от них неотличим.

Проверка без запуска сайта:

```bash

py tests/test_messenger_csv.py       # 11: темы, варианты выгрузки, повтор файла
py tests/test_remains_report.py      # лист «Остатки»: бланк, разметка, счётчики
py tests/test_shift_2609_fixes.py    # аудит 26.09: призрак №151, счётчики, отходы
```

## Защита от опечаток в показаниях счётчика

Счётчик — единственный источник времени работы станка: `часы = (конец − начало)
/ норма / 60`. Одна лишняя цифра ломает весь отчёт, и выглядит это как
катастрофа, а не как ошибка. Прогон 14.09.2026, эталон сверялся с журналом
пользователя:

| Стан | Написал мастер | Было в отчёте | В эталоне |
| --- | --- | --- | --- |
| 321 | `Общ сч 1200807` (лишний 0) | **работа машины 3000,15 ч**, «+2996,32 ч сверх 12 ч» | 0,2 ч |
| 151 | `Общ.сч. 7760351` (лишняя 7) | **работа 0 ч**, «−11,25 ч до 12 ч» | 8,7 ч |

Модель здесь ни при чём — она честно передала то, что написано. Проверка
`services/counter_check.py` ловит опечатку тремя независимыми признаками:

1. **Модальная длина числа.** За смену мастер пишет счётчик много раз. У №151
   было 13 значений: двенадцать шестизначных и одно семизначное — оно и есть
   опечатка. Признак надёжен, потому что счётчик за смену растёт на сотни
   узлов и разрядность не меняет.
2. **Предел выпуска за смену.** `12 ч × норма узлов/мин × 60`. Для №321 это
   ~4320 узлов, а дельта была 1 080 054 — в 250 раз больше.
3. **Сверка с прошлой сменой** (`counter_ledger.json`) — только если запись
   соседняя (не дальше 2 суток), иначе ложная тревога за пропущенные дни.
4. **Хронология сохранённых смен** (лист «Остатки»,
   `remains_report.counter_chronology_warnings`) — общий счётчик станка
   сравнивается со всеми накопленными сменами этого станка до и после. Молчать
   нельзя, когда опечатка повторена в трёх сменах подряд (ст.321:
   118526 за 10.09 → 1200807 за 14–16.09 → 123061 за 21.09): соседнее показание
   такое же испорченное, и правило 3 его не видит. Показание с планом
   («1000 из 1450») в сверку не идёт — это размер среза, а не одометр.

Числа **никогда не подменяются молча**: каждое исправление приходит
пользователю словами («вероятна опечатка, взято 760449… если число верное —
пришлите исправленное показание»). Если доказательств мало (показаний меньше
трёх, нормы станка нет), данные остаются как есть — лучше честное
расхождение, чем выдуманная цифра.

Разделы берутся **только своего станка**: смешивать показания нельзя, у ст.98
счётчик восьмизначный (21420800), а у ст.151 шестизначный (760449) — на общем
тексте мода разъезжается и «исправляет» честные числа.

### Термины участка в причинах простоя

- **Дотягивание** — подстановка сошедших шпулей, чтобы дотянуть ассортимент.
  Постоянная категория отчёта: «простой дотягивание» стоит почти каждый день
  с 19.08 по 14.09 (эталон 14.09, ст.321 — 6,95 ч, самая крупная строка дня).
- **Наладка датчика схода шпули** — это наладка, а не дотягивание и не навивка:
  слово «шпул» в записи описывает предмет наладки (эталон 21.08, 26.08, 04.09).
- **Безымянная служба наладки** («служба наладки вытащила шнур») идёт в
  привлекаемый персонал строкой «наладчик» — в эталоне 14.09, ст.321 стоит
  «0,87 | наладчик — наладка» без фамилии.

### Норма оператора не всегда 11,25 ч

Стажёр работает сокращённую смену. Эталон 14.09, ст.321: оператор Демидов —
«Работа оператора всего **8** из **8** часа», а бот печатал «из 11,25» и
получал ложное превышение +0,75 ч. Модель отдаёт `operator_norm_hours`, когда
норма видна в тексте («смена 8 часов», «из 8 часа»); иначе норму считает код
по времени прихода и ухода.

### Полуинтервалы

«`start` есть, `end` нет» достраивается от начала **следующего** события.
Обратно (начало от конца предыдущего) не достраивается: предыдущая запись
обычно описывает работу машины, и приписать следующему останову её начало —
значит заявить, что станок стоял всё это время. На реальном прогоне так
«Срез узлов» превращался в останов 1,83 ч при эталонных 0,17 ч.

### Средний счётчик — не общий

Валидатор сам создал крупнейший дефект этого прогона (15.09.2026): ветка
«\bсч» ловила и СРЕДНИЙ счётчик, потому что перед «Сч.» стоит граница слова.
Мода длины посчиталась по 12 средним счётчикам (4 цифры) и объявила настоящие
шестизначные показания опечаткой:

| | мастер написал | валидатор «исправил» на | правильно |
| --- | --- | --- | --- |
| ст.251 | `Об. Сч.: 288402` | `4274` (это «Ср. Сч.: 4274 из 14800») | 288402 |
| ст.251 | `Об. Сч:. 291916` | `7788` (это «Ср. Сч.: 7788 из 10000») | 291916 |

Признак среднего/срезового счётчика: подпись «Ср»/«Срез»/«Средний» или
конструкция «N из M». Общий счётчик — «Общ.сч.», «Об. Сч.:», «Общ сч»;
разделители идут в любом порядке (`Сч:.`, `Сч.:`, `Сч:-`), поэтому шаблон ждёт
класс разделителей, а не «точку, потом двоеточие».

**У общего счётчика плана «из скольки» не бывает.** Это накопительный одометр,
мастер пишет его одним числом; дробь под его меткой — соседний счётчик,
подпись которого не узнали. Прогон 21.09.2026, ст.98: «Общий сч.21486750
**Со.сч.1000 из 1450**» (описка в ярлыке — задумано «Ср.») и вечерний итог
«**Общ. Счётчик** 21509000». В «Остатках» стояло 1000 из 1450: точка после
сокращения не узнавалась, поэтому «Общ. Счётчик» не читался вообще, а дробь
из описки считалась «более полным» значением и вытесняла итог смены. Теперь
три правила: сокращение с точкой и полным словом читается, голое «Сч» с
дробным значением общим счётчиком не считается, и для общего счётчика внутри
одного замера главное — ПОСЛЕДНЕЕ показание, а не «полнота» (так же
24.08.2026, ст.251: было `243884 из 15900` — чужой план, стало вечернее
`245915`).

**Значение, повторённое мастером 2+ раза, — не опечатка.** Ст.321 за 15.09:
«Общ сч 1200807» написано трижды (06:55, 07:05 и в конце смены) — счётчик
заменили. Независимые записи одного числа это доказывают, и тревогу о
несовпадении с журналом прошлой смены поднимать не надо.

### Опечатка восстанавливается вычёркиванием цифры

Раньше испорченное число заменялось соседним достоверным показанием — а это
другое измерение, и часы выходят другие. Проверено на эталоне пользователя
(14.09, ст.151): `7760351 → 760351` даёт ровно его 8,7 ч, а подстановка
следующего показания 760449 — 8,59 ч. Теперь лишняя цифра **вычёркивается**,
а кандидат отбирается монотонностью (счётчик за смену только растёт):
для начала — от прошлой смены до первого достоверного показания, для конца —
от последнего показания до «последнее + выпуск за смену». Если однозначного
кандидата нет, число не трогают вовсе.

### Норма выработки уточнена по файлу пользователя

`machine_rates.json`: №151 = **10,9** и №251 = **7,35** (колонка T файла
«выгрузка за 15 число моя.xlsx», лист «15.09.2026»). Контроль формулой:
ячейка O11 пользователя `=N11/T11/60` = 3514/7,35/60 = **7,968253968253969** —
совпадает дословно. Со старыми 7,4 выходило 7,91 ч. Норма №151 менялась со
временем: за 26.08 эталон требует 10,4, с 09.09 по 15.09 — 10,9; тесты поэтому
считают ожидаемые часы ОТ СПРАВОЧНИКА, а не хардкодом.

### Правила разбивки времени

- **Обед (45 мин) всегда отдельная строка простоя**, и он вырезается из окон
  простоя, которые его накрывают. Прогон 15.09.2026, ст.321: окно
  07:00–16:20 «машина на подмене» съедало обед, строка обеда снималась тримом
  как задвоение, и «отсутствие оператора» недобирало 0,75 ч (2,67 вместо 3,0).
- **Смена оператора короче смены станка** → остаток идёт в «отсутствие
  оператора» (ушёл в 16:20 → 2,67 ч отсутствия, баланс всё равно 12 ч).
- **Работа станка + строки простоя = 12 ч** — инвариант, по которому отчёт
  сверяется с журналом пользователя.
- **Сменная операция-обёртка** («машина на подмене» на всю смену) не должна
  дублировать подробные записи, а 45 мин обеда из неё вырезаются: ст.321 за
  15.09 давал оператору 9,33 ч вместо 8,58.
- **Нет выпуска за смену → нет «контроля за работой машины».** Ст.111 за
  15.09: Дремкова весь день подменяла шпули, станок не дал ни узла, а бот
  добивал ей 7,05 ч контроля и выдавал 11,25 вместо эталонных 3,92. Проверено
  по журналу: из 117 блоков с нулевой работой машины строка «контроль» не
  встречается ни разу.
- **«Нужна консультация наладчика», «требуется помощь наладчика» — это
  ЗАПРОС, а не часы службы.** Ст.251 за 15.09: событие 15:58–16:21 ушло в
  kind «наладка» и дало лишнюю строку «0,38 | наладчик», которой в эталоне
  нет (там только «0,88 | Пронкин»).

### Плавающий обед (введён на участке 16.09.2026)

Мастер написал в блоке «Данные из чата»: «Сегодня на участке проводим
эксперимент по внедрению плавающего обеда … оборудование N 321 N 151,
операторы Петровский О и Демидов Е под контролем Погодиной Л.Е.». Операторы
обедают в РАЗНОЕ время и на свой перерыв передают станок коллеге — машина
продолжает работать, простоя нет:

| перерыв | кто принимает |
|---|---|
| Демидов 11:00–11:45 | Петровский принимает N 321, «не останавливает N 151» |
| Петровский 11:45–12:30 | Демидов принимает N 151 |
| Вашурина 12:45–13:30 | Петровский принимает N 251 |

В эталоне пользователя за 16.09 строки «простой обед» нет у ст.321/151/251, а
у ст.98 есть (0,75 ч) — там обед никто не принимал. Код снимает строку обеда,
когда мастер написал, что станок приняли/не останавливали (`lunch_handed_over`,
`_LUNCH_HANDOVER_RE`), либо когда модель вернула `machine_kept_running: true`.

Три следствия, которые тоже пришлось чинить:
- **Окно обеда — своего оператора.** В разделе №151 первым шло событие
  «обеденный перерыв Демидова Е. 11:00–11:45», код брал его окно и вырезал
  45 мин у Петровского, хотя его перерыв 11:45–12:30. Теперь окно берётся по
  `performer == operator` (`lunch_window_mine`).
- **Прикрытие на обед — не привлечённый персонал.** «Петровский — принял 321 на
  время обеда Демидова» 0,75 ч уходило в «Работу привлекаемого персонала»
  (3,02 ч вместо эталонных 2,17). Это взаимный обмен: часы стоят в блоке того,
  кто работал (`_LUNCH_COVER_RE`). Обычная помощь в середине смены по-прежнему
  считается — «2,52 Петровский — замена шпулярника 101 шт» на №251 осталась.
- **`other_machine` у чужого исполнителя — это ОТКУДА он пришёл.** Событие
  {kind «навивка», performer «Петровский», other_machine «151»} код трактовал
  как «Демидов ушёл на 151» и рисовал отсутствие 4,98 ч + вписывал Демидову
  0,75 ч чужой навивки.

### Записи без времени и конец смены

Твоё предположение про отсутствующее время подтвердилось: из 37 событий за
16.09 модель вернула 3 без времени (8%) — «отходы НПА 187х2 6,2 кг» (ст.111),
«оборвало нить верхней основы, устранил» (ст.151), «замена шпулярника в
течение смены» (ст.98). Именно они создали все ложные флаги:

- **ст.111: отходы не доказывают оператора.** Единственная запись про
  килограммы отходов завела строку ассортимента без счётчиков → `has_operator`
  стал True, норма 9,52 ч, и бот начислил несуществующему человеку 9,52 ч
  «контроля за работой машины» + 0,75 обеда. Теперь строка ассортимента сама
  по себе оператора не доказывает — нужны операции или показания счётчика.
- **ст.151: «Стоп. Обрыв нити» без времени.** Станок отработал 11,61 ч из 12,
  остаток 0,39 ч валился в «прочее» и давал ложный флаг «станок −0,39 ч до
  12 ч». Малый остаток (≤1 ч) при единственной названной причине теперь идёт к
  этой причине. Добавлена категория «обрыв нити» — у тебя это отдельная строка
  («0,18 простой обрыв»), а код отправлял её в «прочее».
- **ст.251: «7:00-15:39 подставляла шпулярник»** (8,65 ч при работе 5,73 ч) не
  влезает в 12 ч и оставляется параллельным — но остаток 1,29 ч теперь
  объясняется той же причиной (эталон: «2,85 простой замена шпул»), а не
  «причина не указана» с флагом «−1,29». БОЛЬШОЙ остаток без времени честно
  остаётся необъяснённым (эталон 02.09 ст.321: 10,95 ч и подпись «время не
  указано у причин: …»).
- **ст.321: конец смены выдуман.** Раздел заканчивается «16:00-16:15 заполнение
  журнала и чата», ни «19:00», ни «конец смены» в нём нет, а модель вернула
  `operator_shift_end = "19:00"`. Хвост 16:15–19:00 не становился «отсутствием
  оператора», баланс съезжал на 9,13 ч, 2,87 ч уходили в «причина не указана».
  Теперь: если «19:00» не подтверждено текстом (`model_shift_end_
  unconfirmed`), конец присутствия берётся из завершающей записи мастера.

Отдельно чинились три системные ошибки:
- **События `kind "работа"` своего оператора выбрасывались целиком** — 69 таких
  записей по всем дням (приём сырья, перестановка телег, заполнение журнала,
  культура производства). На станке с нулевым выпуском филлер «контроль» не
  работает, и Демидов потерял 1,53 ч: 6,76 вместо эталонных 8,58.
- **Филлер «наладка (весь день)» при 1% наладки.** Ст.321 за 16.09: наладка
  0,10 ч из 9,78 ч простоев, а код добавил 2,22 ч «наладка весь день», которого
  в эталоне нет. Теперь наладка обязана составлять ≥50% простоев.
- **`handover_coverage_hours` брал сумму часов, а не время.** Гузеев (13:20–15:30)
  и Петровский (11:00–11:45) «покрыли» хвост 16:15–19:00, хотя оба закончили
  раньше. Теперь учитываются только окна, попадающие в хвост.
- **Лист «Остатки»: «Общий сч.21453550 7срезов» → 214535507.** Жадный класс
  `[\d \t]*` склеивал счётчик со следующим значением. Пробел теперь считается
  разделителем тысяч только перед ровно тремя цифрами: «12 345» и «21 453 550»
  сохраняются, «21453550 7срезов» разделяется.

### Автор сообщения — не обязательно оператор станка

В выгрузке чата перед каждой записью стоит подпись отправителя, и часто это
**не** тот, кто стоит у станка. Прогон 15.09.2026, ст.98: в переписке фамилии
оператора нет вовсе, есть только авторы записей — «Юлия Черныш, 06:57» (замер
счётчика) и «Нина Владимировна Дроздова, 07:44» (сводка по станку). Модель
поставила `operator = "Дроздова"`, а у пользователя оператором ст.98 за этот
день стоит Симонова: операторы 98-й чередуются по двое суток (Белякова/
Симонова), и их фамилии в чате может не быть вовсе. За все 28 дней журнала
Дроздова ни разу не была оператором.

Отличие — по содержанию: оператор пишет о своей работе **от первого лица**
(«приступаю к навивке», «меняю шпули», «иду за сырьём», «заполняю журнал»),
а мастер смены — безличным перечислением («Общ сч 21431800, Ср. 750, Всего 8
срезов, Навито 160 шп»). На прогоне 15.09 у Дроздовой 0 таких маркеров, у
Демидова 6, у Арташиной 18.

Фамилию код **не стирает** (иногда мастер смены действительно ведёт станок) —
он поднимает предупреждение: «№98: „Дроздова" встречается только как ПОДПИСЬ
АВТОРА сообщений — возможно, это мастер смены, а не оператор станка». Проверка
молчит на 10.09, 14.09 и 26.09 — ложных срабатываний нет.

```bash
py tests/test_etalon_1409.py     # 18 проверок по сравнению с эталоном 14.09
py tests/test_etalon_1509.py     # 17 проверок по сравнению с эталоном 15.09
py tests/test_etalon_1609.py     # 21 проверка: плавающий обед, записи без времени
```

## Что распознаёт парсер

- Номер станка (в т.ч. в форматах `– 251`, `98 станок`)
- Время начала и конца смены (форматы `08:46`, `08.46`, `08;46`, `18-20`, `7ч`)
- Общие и срезовые счётчики
- Дроби вида `1362 из 2030`, `34 из 304`, `3 из 3`
- Количество шпуль (`502 шт.`) и привязанных узлов (`1261 узл.`)
- Подмены операторов с указанием количества
- Остановки и запуски машины
- Предупреждения при пропусках («нет данных», «отсутствует», «пропуск»)

## Логирование

Логи сохраняются в файл `logs/web.log`. Уровень логирования настраивается
через `LOG_LEVEL` в `.env`.

## Безопасность

- Никогда не коммитьте файл `.env` в репозиторий
- Ключ ИИ (`AI_API_KEY`) хранится только в `.env` на рабочем компьютере
- Сайт слушает `127.0.0.1`: доступ к переписке и счётчикам имеет только тот,
  кто сидит за этим компьютером. `WEB_HOST=0.0.0.0` открывает сайт всей сети —
  пароля на нём нет, поэтому так стоит делать осознанно
- Файлы для скачивания отдаются только из архива отчётов и папки выгрузок:
  имя чищается до базового, чужой путь возвращает 404
- Используйте `.gitignore` для исключения конфиденциальных файлов
