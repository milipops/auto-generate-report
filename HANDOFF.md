## Что это за проект

`ForWorkTest` — локальный сайт на Python (HTTP-сервер на stdlib, без
внешних сервисов), который принимает свободную переписку мастеров намоточного
участка по станкам и собирает **отчёт производства за смену** по каждому
станку, один в один как я делаю руками в Excel. Репозиторий:
https://github.com/zamaletdinovr575-web/ForWorkTest.git

Раньше это был Telegram-бот. Функции переехали на сайт без изменений, а папка
`bot/` удалена вместе с зависимостью `aiogram`.

Пайплайн (не переделывать, он выстроен и проверен):

```
сообщения (страница сайта или Яндекс Мессенджер)
   → накопитель смены data/shifts/<ДД.ММ.ГГГГ>/day.json   (без ИИ, бесплатно)
   → ОДИН вызов ИИ по кнопке «Собрать отчёт» — модель отдаёт ТОЛЬКО структуру
   → детерминированный Python считает часы и суммы
   → текстовый отчёт по каждому станку + файл .xlsx + файл для 1С
```

Ключевая идея архитектуры: **ИИ достаёт структуру, арифметику считает код.**
Нейросети нельзя доверять числа — она делит переписку по станкам, выкидывает
мусор чата и читает распознанный текст, а часы, выпуск и балансы считает
Python. Не смешивай эти роли.

## Незыблемые правила расчёта (я их задавал, не меняй)

1. **Время работы станка считается по счётчику, а не по времени сообщений:**
   ```
   Выпуск, узл.    = счётчик_конечный − счётчик_начальный
   Время работы, ч = Выпуск / T / 60      где T — норма узлов в минуту
   ```
   `T` берётся из `services/machine_rates.json`.
2. **Справочник норм ПОЛНЫЙ** — 9 станков участка: 98, 111, 121, 151, 251,
   321, 601, 14тр, 15тр. Не спрашивай у меня нормы, их больше нет. Если в
   переписке номер, которого там нет, — это опечатка мастера, так и пиши.
3. **Смена 07:00–19:00**, норма станка 12 ч. Норма сотрудника считается от
   конца ЕГО смены минус обед (45 мин, или 30 мин при смене до 15:30) минус
   часы, отработанные на другом станке.
4. **Допуск 20 минут.** Расхождение до 20 мин — норма, больше — пометка
   «⚠️ НЕДОСТАТОК ВРЕМЕНИ» отдельно по станку и по сотруднику.
5. **Причины простоя — словами мастеров**, дословно («стоит, навиваю шпули»,
   «крючок не взял петлю»). Не переписывай их «красиво».
6. **Нет данных — пиши «нет данных».** Если нет нормы или нет пары показаний
   счётчика, время работы неизвестно: отчёт пишет «⛔ Баланс времени не
   считаю», а не выдумывает недостаток в 12 часов. Это была реальная ошибка,
   которую мы уже исправили — не возвращай её.
7. **Excel обязателен вместе с каждым отчётом.** Три листа: «Отчет за смену»
   (мой бланк, колонки A–T, выпуск и время — формулами `N=M−L`, `O=N/T/60`),
   «Простои по причинам», «Итоги смены» (балансы через `SUMIFS`).

## Правило для фотографий (свежее, реализовано)

Фото в чате чаще всего «показать, что сделано» — моток материала, катушка.
Поэтому каждое фото на приёме проходит **бесплатный локальный OCR**
(Tesseract, `services/photo_ocr.py`), и дальше три ветки:

- **текста нет** → фото не сохраняем и в ИИ не отправляем;
- **текст рабочий** (счётчик, время, дробь «1362 из 2030», слова смены) →
  в запрос к ИИ уходит **распознанный текст, а не картинка** (картинки в
  запросе дороже, я просил так);
- **текст есть, но не про работу** → в отчёт не идёт, сайт показывает его
  отдельным блоком «📎 Постороннее с фотографий».

Если Tesseract не установлен — фото **не теряются**: уходят в ИИ картинкой,
сайт один раз предупреждает. Выключатель `OCR_SEND_PHOTOS_TO_AI=true` в `.env`
возвращает картинки в запрос, если Tesseract будет плохо читать рукописный
журнал.

## Как проверять работу

В проекте ~40 автономных тестов на чистом stdlib, без сети и без pytest.
**После любой правки прогоняй все сразу:**

```bash
python tests/_run_all.py
```

Печатает ✅/❌ по тестам и в конце итог `ran N failed M`. Ориентир сейчас —
`ran 313 failed 1`: единственная красная строка, `test_excel_export.py::
test_structure_and_values`, известная и старая (проверка ожидала лист
«Пояснение 19.08»), она краснела ещё до перехода на сайт. Всё остальное
обязано быть зелёным.

Отдельные файлы, которые чаще всего нужны:

```bash
python tests/test_webapp.py            # сайт целиком: приём, сборка, архив, HTTP
python tests/test_site_flow.py         # сценарий смены: приняли → отчёт + файлы
python tests/test_database_web.py      # база сайта: люди, журналы, записи
python tests/test_day_pipeline.py      # сборка дня: накопитель → ИИ → файлы
python tests/test_report_archive.py    # архив готовых файлов за дату
python tests/test_shift_report.py      # формула по счётчику, допуск 20 мин
python tests/test_excel_export.py      # структура бланка и формулы
python tests/test_photo_ocr.py         # фильтр фото: пусто / рабочий / посторонний
python tests/test_yandex_source.py     # приём из Мессенджера по обсуждениям
```

`test_day_19_08_2026.py`, `test_day_20_08_2026.py`, `test_etalon_*.py` —
регрессия на настоящей переписке и на моих эталонных журналах; они ловят как
раз те ошибки, из-за которых отчёт врал. Если что-то из них краснеет —
виновата твоя правка, а не тест.

Сайт запускается без сети и без мессенджеров: `python main.py` (нужны только
зависимости из `requirements.txt`). В песочнице с сетью нельзя только вызовы
ИИ — тесты подменяют сборку или ставят `AI_ENABLED=false`. Логи —
`logs/web.log`.

Для человека без консоли есть сборка в .exe:
`py -3.11 -m PyInstaller --noconfirm --distpath . production-reports.spec`
(подробности — в README, раздел «Запуск без консоли»). Важно помнить: `.exe` —
это слепок кода на момент сборки, после любой правки его нужно пересобрать, а
сам он кладётся в корень проекта, рядом с `.env`, `data/` и `logs/` (ищешь свои
файлы по папке, где лежишь — `runtime_paths.py`). В git он не попадает.

И вторая половина той же ловушки, из-за которой «меняю модель в `.env`, а в
логе прежняя»: `.env` читается один раз при старте процесса, а повторный клик
по `.exe` — не перезапуск (порт занят, страница открывается у прежнего
процесса). Поэтому модель и формат ИИ печатаются в шапке лога и в бейдже на
странице (`api.state()` → `ai_model`), а `AI_MODEL` должен быть точным id у
шлюза, не именем с пробелами.
